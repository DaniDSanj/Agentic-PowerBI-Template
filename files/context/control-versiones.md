# Control de versiones autónomo

## Modelo de ramas: `dev` como integración obligatoria, `main` protegida

- **`main` nunca recibe una PR directa de `feature/`/`fix/`**: está protegida (branch protection vía `tools/setup-github.ps1`) y solo acepta una PR cuya rama origen sea `dev` o `release/*` — lo hace cumplir el job de CI `source-branch-gate` (`.github/workflows/validate-pr.yml`), marcado como required status check, porque GitHub no tiene un mecanismo nativo de branch protection para restringir la rama origen de una PR.
- **`dev` es la rama de integración**: todo `feature/<nombre>`/`fix/<nombre>` nace de `dev` (no de `main`), y su PR de cierre va contra `dev`. `dev` también está protegida (PR obligatoria + CI en verde vía los checks `validate`/`gitleaks`) — sin push directo, ni siquiera del agente (`permissions.deny` en `.claude/settings.json` lo bloquea técnicamente).
- **Promoción `dev → main`**: es un paso humano y explícito, separado del cierre de cada unidad de trabajo — se abre cuando `dev` acumula cambios listos para publicar (no en cada commit). El agente puede abrir esa PR, pero **nunca la mergea** (igual regla que cualquier otra PR, ver más abajo).
- Commits semánticos; PR con revisión explícita del diff TMDL antes de mergear; haz `pull` antes de `push`; nunca cambies de rama con el PBIX abierto en Desktop.
- **Azure Repos/Azure Pipelines** es la alternativa equivalente cuando el repo externo ya use Azure DevOps: mismo flujo de branching y commits (con `dev` cumpliendo el mismo papel de rama de integración), con Deployment Pipelines sustituyendo a GitHub Actions en Escenario B.
- Mantén el control de versiones de forma autónoma (commitear, abrir PRs contra `dev`) salvo objeción explícita del usuario para ese repo concreto.

## Escaneo de secretos (tres capas)

- **GitHub secret scanning + push protection nativos** (`security_and_analysis` del repo, habilitados vía `gh api`): gratis porque el repo es **público** — bloquean el propio `git push` si el patrón de un proveedor conocido se detecta, antes de que el commit llegue al remoto.
- **CI (`gitleaks`, bloqueante)**: el job `gitleaks` de `.github/workflows/validate-pr.yml` escanea el diff completo de cada PR y es required status check en `main`/`dev` — cubre patrones no cubiertos por el escáner nativo de GitHub y actúa como red de seguridad independiente.
- **Local (`gitleaks`, best-effort)**: el hook `PreToolUse` `.claude/hooks/pre-commit-secrets-check.ps1` corre `gitleaks` sobre el staged antes de cada `git commit` **si el binario está instalado en la máquina** — y no lo instala nadie por defecto. Si no está, el hook avisa y deja pasar sin bloquear (nunca se reporta una verificación local que no se hizo); esta capa solo se activa de verdad tras el paso manual de instalación que el README lista junto al resto de la toolchain (TE2, DAX Studio). Hasta que se instale, la única protección real en esa máquina es CI + push protection nativo — no asumir que el hook local está haciendo algo si nadie ha instalado `gitleaks` ahí.

**Hallazgo real de esta sesión, no una elección de diseño**: se intentó mantener el repo privado y usar solo `gitleaks` como alternativa gratuita a GitHub Advanced Security. Al ejecutar `tools/setup-branch-protection.ps1` contra el repo privado, la API de branch protection (clásica y rulesets) devolvió `403 Upgrade to GitHub Pro or make this repository public` — **branch protection en sí, no solo el secret scanning nativo, requiere GitHub Pro o visibilidad pública en un repo con plan Free**. Confirmado con `gh api .../branches/main/protection` (GET) tras el intento fallido. El usuario decidió hacer público el repo (plantilla sin datos de cliente ni credenciales) en vez de pagar GitHub Pro; `gh repo edit --visibility public` lo aplicó y desde entonces la branch protection y el secret scanning nativo funcionan de verdad (verificado con GET, no solo con el exit code del script).

**Corrección posterior, mismo hallazgo real**: el mismo script, al terminar, cambiaba también el `default_branch` del repo a `dev` (para que las PRs apuntaran ahí por defecto). Eso rompía "Use this template": GitHub solo copia el `default_branch` salvo que se marque "Include all branches", así que un repo cliente nuevo habría nacido con una sola rama (`dev`) y **sin `main`**. Corregido: el script ya no toca `default_branch` — se mantiene en `main` siempre (ver sección siguiente).

**Fusión posterior en un único script**: `tools/setup-branch-protection.ps1` se renombró a `tools/setup-github-repo.ps1` y ganó un modo de creación (`-ClientName`): ya no hace falta crear el repo cliente con `gh repo create`/"Use this template" y luego ejecutar el script por separado — un solo comando crea el repo, lo clona, protege `dev`/`main`, y activa el secret scanning nativo si el repo es público (ver ejemplo en el README).

**Segunda fusión posterior, a petición del usuario**: `tools/setup-github-repo.ps1` y `tools/setup-local-git-guard.ps1` (ver sección "Escenario privado (Free)" más abajo) se unieron en un único `tools/setup-github.ps1`, para tener un solo punto de entrada de gobernanza de repo. No es un simple pegado: la parte de GitHub requiere `gh` autenticado con permisos de **administrador** del repo, mientras que activar el guard local no requiere ningún permiso especial — un colaborador con acceso de solo escritura, o el propio administrador autenticado con un token de alcance reducido (fine-grained PAT sin el permiso `administration`), no podrían activar su guard local si el script intentase siempre primero la parte de GitHub. Por eso el script fusionado gana un modo `-LocalGuardOnly` que salta por completo la parte de GitHub (no requiere `gh` ni instalado); y cuando se ejecuta en sus modos normales sobre un repo privado, activa automáticamente el guard local en ese mismo clon al terminar. **Diseño, pendiente de su propio dogfooding real** — mismo criterio de honestidad que el resto de esta sección.

## Escenario privado (Free) — capa de gobernanza local

Recomendación (no exigencia) recogida en una sesión de documentación automatizada: un repo cliente real puede preferir visibilidad **privada** por confidencialidad de datos de negocio (KPIs, nombres de tabla, roles RLS). El problema, ya documentado más arriba con evidencia real: en GitHub Free, un repo privado no puede tener branch protection (403 confirmado) ni secret scanning nativo gratis. Esta sección documenta la mitigación **local** diseñada para ese caso — hooks de git nativos, no de Claude Code — y, con la misma honestidad que el resto de este fichero, su límite exacto.

**Diseño, no todavía dogfooding real** (a diferencia del resto de este fichero): lo que sigue es la contraparte razonada de un hallazgo real, pendiente de su propia validación en un repo cliente privado real — mismo criterio que el resto de la plantilla aplica a cualquier pieza nueva (ver la nota final de `flujo-trabajo.md`).

### Qué añade `tools/git-hooks/` (activado por `tools/setup-github.ps1 -LocalGuardOnly`)

- `pre-commit` — corre en **todo** `git commit` de ese clon, sin importar quién lo haga (agente o humano) — a diferencia de `.claude/hooks/pre-commit-secrets-check.ps1`, que solo ata al agente. Bloquea si `gitleaks` detecta un secreto staged; si `gitleaks` no está instalado, bloquea también (fail-closed) cuando `.claude/project-config.json`.visibilidad es `"privado"` — en público sigue avisando y dejando pasar, porque ahí el secret scanning nativo de GitHub sigue cubriendo esa capa gratis.
- `pre-push` — bloquea siempre un push directo a `refs/heads/main`, `dev` o `release/*` (repone, a nivel de "cualquiera que use este clon", lo que `permissions.deny` solo hace para el agente), y sobre cualquier otra rama corre en local, antes del push, los mismos scripts que corre CI (`validate-pbir-schema.ps1`, `validate-docs-freshness.ps1`, `validate-bpa.ps1` si Tabular Editor 2 es localizable) más `gitleaks detect` sobre el rango que se va a empujar.
- `core.hooksPath` es configuración **local** de cada `.git/config` — no viaja con el repo. Cada clon (incluido uno nuevo tras "Use this template") debe ejecutar `tools/setup-github.ps1 -LocalGuardOnly` una vez, exactamente igual que instalar `gitleaks`/Tabular Editor 2 (paso manual, `files/context/limites-duros.md`) — salvo que ese clon sea el mismo desde el que se ejecutó `tools/setup-github.ps1` en modo GitHub sobre un repo privado, en cuyo caso ya se activó automáticamente ahí. El modo `-LocalGuardOnly` existe precisamente para quien no tiene (o no quiere usar) permisos de administrador del repo: un colaborador con acceso de solo escritura, o un administrador autenticado en `gh` con un token de alcance reducido. El skill `local-git-guard` automatiza esta invocación dentro de una sesión de Claude Code.

### Lo que esta capa NO puede cerrar bajo ninguna circunstancia

El botón **Merge** de la UI web de GitHub se ejecuta en el servidor. Sin branch protection real, nada impide técnicamente que alguien con permiso de escritura mergee una PR con CI en rojo desde el navegador, o edite un fichero directamente en la web (commit que nunca pasa por un `git push` local). Ningún hook de git, sea este o cualquier otro, puede interceptar eso — no es un hueco de implementación, es una limitación de plataforma. La mitigación para esto es **detección a posteriori, no prevención**: el subagente `merge-audit` (skill `audit-history`) revisa el historial de merges de `main`/`dev` en busca de commits sin PR asociada o con checks de CI que no estaban en verde, y lo reporta — nunca lo corrige en silencio.

**No presentes esta capa como equivalente a branch protection real** en ninguna conversación con el cliente: es una mitigación con un hueco residual documentado, útil y real dentro de su alcance, pero no un sustituto. Si el cliente necesita cerrar también el hueco de la UI web, las únicas opciones son las ya descritas más arriba (repo público, o GitHub Pro/Team de pago con autorización explícita).

## Reaplicar esto en un repo cliente

Un repo creado con "Use this template" **no hereda la configuración del repo** (branch protection, `security_and_analysis`, webhooks, secrets de Actions) — solo copia ficheros. Y de las ramas, **copia únicamente la rama por defecto (`main`)**, no `dev`, salvo que se marque explícitamente "Include all branches" al crear el repo (botón web) o se pase `--include-all-branches` a `gh repo create` — **no lo marques/pases**: es el comportamiento esperado, no una laguna. `dev` no necesita venir copiada porque `tools/setup-github.ps1` ya sabe crearla desde `main` si no existe. El flujo recomendado es dejar que el propio script cree el repo cliente (`-ClientName`); si el repo ya existe (por ejemplo, esta misma plantilla), ejecuta el script sin ese parámetro desde su carpeta para crear/proteger `dev` y `main` ahí también.
